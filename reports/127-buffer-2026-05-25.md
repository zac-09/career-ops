#### 12. Describe an API/SDK you've recently designed from scratch. What design decisions did you make and why?

> The closest fit is a gRPC service bus I designed at CodeBits to let independent USSD providers in Uganda talk to a central legal-aid backend run for FIDA and LASPNET. The hard problem wasn't the wire format — it was that we couldn't control the providers, so the contract had to be stable enough that they could integrate once and not come back. Three decisions stand out. First, protobuf with explicit version fields on every message, so we could evolve the schema without breaking older clients. Second, gRPC for the synchronous "intake a new case" calls but Kafka events for everything async (case updates, status changes), so providers didn't block on our backend being healthy. Third, idempotency keys on every write, because USSD sessions drop constantly and retries had to be safe by default. The result was that new providers could integrate in days instead of weeks, and we never had to do a per-provider custom branch. The thing I'd carry into Buffer's public API work is that schema-first, versioned-from-day-one design pays compound interest — every "small" field becomes a contract, so it's worth being deliberate.

#### 15. Tell us about a time when you were wrong about something at work. What happened, and how did you handle it?

> Early in the MTailor Parse→Firebase migration I was convinced we could do a single-cutover weekend migration — drain traffic Friday night, run the export, switch DNS Monday morning. I'd done one-shot migrations before and the math looked clean. Two weeks of dry runs proved me wrong: the dataset was bigger than our backup window, the customer-facing apps had no graceful read-only mode, and a single bad batch would have meant rolling back to Parse with stale data. I told the CTO I'd been wrong about the approach and proposed the opposite: build a real-time two-way MongoDB↔Firestore sync with Pub/Sub, run both systems in parallel for weeks, and migrate services one at a time with the ability to flip any single service back instantly. That added about six weeks of engineering work but it's the reason we completed 20+ apps with zero downtime instead of explaining a Monday-morning outage to customers. The lesson I keep returning to is that the cost of being wrong about migration architecture is asymmetric — slow and reversible beats fast and one-shot, almost every time.
